# Research: `shrine bump`

**Feature**: 036-bump-command | **Date**: 2026-10-07

No `NEEDS CLARIFICATION` markers existed in the Technical Context. The epic design settles every choice of substance (section 4.6, decisions TD-8 and TD-12); the entries below record how each lands in the codebase as it is on `main` after T5 (#64), the places where the design's wording needed refinement against the code, and the alternatives rejected. Decisions TD-1 to TD-13 are not reopened.

## R1. The manifest set is loaded and planned the way deploy does it

**Decision**: `handler.Bump` and `handler.BumpDryRun` call `planner.LoadDir(dir)`, look the artifact up in the loaded set by kind and name, and then run `planner.Plan(set, store.Teams, cfg.Registries, ports, filter, cfg.ImagePullPolicy)` with `planner.ByApp(name)` or `planner.ByResource(name)`. The planning call, the host-port context, and the printing of `Validation errors:` to `errOut` followed by the `Spec validation errors` error move out of `Deploy` and `DryRun` into one unexported helper, `planManifestSet(errOut, set, store, cfg, filter) (planner.PlanResult, error)`, which the three callers share. After `Plan`, every manifest in `result.ManifestSet` carries its effective policy in `Spec.ImagePullPolicy`, which is what the refusal of R-05 reads.

**Rationale**: TD-12 says bump "loads manifests the way deploy does to read the policy and the repository". `applyEffectivePullPolicy` is unexported and runs inside `Plan`; running `Plan` is the one public way to obtain the effective policy and keeps the T3 and T4 validation rules (fixed version under `Pinned`, configuration-sourced remedy) in force, so a bump never succeeds on a set a deploy would reject at planning time, which is the spec's edge case for an invalid directory. Three callers of the same planning sequence make the extraction a constitution VII requirement, and the extraction is behaviour-preserving for `deploy`. Running the enrichment and collision checks that `Plan` also performs costs nothing measurable at homelab scale.

**Alternatives considered**: exporting `planner.ApplyEffectivePullPolicy` and skipping `Plan` was rejected because it would give bump a second, weaker notion of "the set deploy would load" and leave the fixed-version rules unapplied. Reading `spec.imagePullPolicy` raw from the manifest was rejected because the configuration default (T4) would be ignored.

## R2. Finding the artifact, `--team`, and the ambiguity that cannot happen

**Decision**: the lookup is `set.Applications[name]` or `set.Resources[name]`, chosen by `opts.Kind`. Absent: `application "x": no manifest found in <dir>` with the resolved directory. With `--team`, the manifest's `metadata.owner` must equal it, else `application "x" not found in team "t" (its manifest in <dir> is owned by "u")`. There is no ambiguity error because there can be no ambiguity: `ManifestSet` is keyed by name and `MergeManifest` rejects a second manifest of the same kind and name, so a name identifies at most one artifact per directory. The lookup happens before planning, so an unknown name is reported with the directory rather than with `Filter.Validate`'s `not found in manifest set`.

**Rationale**: PRD R-21 asks for "the usual automatic search and ambiguity error", and design section 4.6 says "using `--team` against `metadata.owner` when several match"; both describe the state-backed lookups of `describe` and `delete`, which search per-team files. Bump searches a manifest directory, where uniqueness is enforced at load time. The spec's scenario for an ambiguous name is therefore unreachable, and the honest contract is "`--team` narrows and verifies". Recorded as a design refinement.

**Alternatives considered**: searching every team's deployment records or pins to honour `--team` was rejected because bump works for undeployed artifacts with no record (R-24). Treating `--team` as ignored was rejected: a wrong team should be an error, as it is elsewhere.

## R3. Target construction, version validation, and one repository helper

**Decision**: the target is `manifest.RepositoryOf(image)` plus `":" + version` for a tag, `"@" + version` for an exact version, and the manifest's own image when `-v` is empty. `RepositoryOf(ref)` is a new exported helper in `internal/manifest` beside `TagOf`, `DigestOf`, and `IsDigestReference`: it cuts a digest suffix, then a tag after the last slash. The private `repositoryOf` in `docker_image.go` and `repositoryWithoutVersion` in `planner/policy.go` are the same function and are replaced by it. `-v` is validated before anything else by `validateBumpVersion`: a tag matches `^[A-Za-z0-9_][A-Za-z0-9_.-]{0,127}$`, an exact version matches `^sha256:[0-9a-f]{64}$`; anything else, including a full reference with a repository, is `invalid version "<v>": use a tag (a letter, digit, or underscore, then up to 127 letters, digits, underscores, dots, or dashes) or an exact version "sha256:<64 hex>"`. For a Resource the image is `res.Spec.Image`, which the parser always fills (`<type>`, `<type>:<version>`, or the operator's override), so a Resource and an Application are built from one field each.

**Rationale**: design section 4.6 step 3 fixes the construction and the two patterns. R-22's guarantee that a bump can never point an artifact at a different image is what the validation enforces: a slash or an `@` in `-v` is rejected, so the repository can only come from the manifest. Three readers of "repository of a reference" (planner validation, the Docker backend, and now the handler) meet constitution IV's bar for one shared helper, and VII forbids a third copy.

**Alternatives considered**: accepting a full reference in `-v` and checking that its repository equals the manifest's was rejected as a second way to say the same thing with a new failure mode. Leaving `repositoryOf` in the backend and importing `dockercontainer` from `handler` was rejected: the handler would depend on the Docker package for a string function.

## R4. `Repin` on the op, and the fourth branch of `ResolveImage`

**Decision**: `engine.ResolveImageOp` gains `Repin string`, the target reference as the handler built it (alias form allowed, unexpanded), and `engine` gains `ImageSourceRepinned = "repinned"`. In `DockerBackend.ResolveImage`, after expanding `op.Image`: when `op.Repin` is non-empty and the policy is `Pinned`, the backend expands `op.Repin` the same way, emits `image.resolve` started with `ref` = the expanded target, and calls `pinReference(ctx, op, target, engine.ImageSourceRepinned)`; `pinNewest` becomes `pinReference(ctx, op, ref, engine.ImageSourceResolved)`, so the pull, inspect, digest pick, no-digest error, and `Put` are written once. A `Repin` under a manifest-owned policy returns `repin of <team>/<name> requires the Pinned policy, got <policy>` before any event. The resulting pin has `Requested` = the expanded target (`…/whoami:v2`, or `…/whoami@sha256:…` for a digest bump) and `Pinned` = `RepositoryOf(target) + "@" + digest`; `ResolvedImage` carries `Source: repinned` and `Requested` = the target, so the finished event renders through the new terminal arm.

**Rationale**: TD-8 makes the backend the only writer of pins; design section 4.2 point 4 names the branch and 4.6 step 4 names the field. The repin branch is the first-deploy branch with a different reference and source, which is why one helper serves both. Failing on the pull leaves the pin untouched because `Put` runs after the inspect, the same ordering T3 established (constitution VI).

**Alternatives considered**: a separate `RepinImage` method on `ContainerBackend` was rejected: it would add a method to the interface and a no-op to the dry-run backend for a branch that already exists. A boolean `Repin` with the target in `op.Image` was rejected because the op would then lose the manifest reference, which the error wrapping and the repository check need.

## R5. A bump bundle with no engine, and a dry run that builds nothing

**Decision**: `app.BumpBundle{Out, ErrOut, Cfg, Store, Paths, SpecsDir, Observer, ContainerBackend}` and `app.BuildBumpBundle(cfg, store, paths, manifestDir, out, errOut)`, which validates registries, resolves the specs directory, builds the terminal and file-logger observer pair, and builds the container backend through `newContainerBackend`, in that order, unwinding the file logger on failure as the other builders do. No Traefik plugin, no vault, no routing, no engine. `--dry-run` follows `deploy`'s shape: `cmd/bump.go` calls `handler.BumpDryRun(out, errOut, dir, store, cfg, opts)` without building a bundle, so no Docker client is constructed and no log is opened; the dry-run handler shares `prepareBump` with the real one and ends by printing `[dry-run] would resolve <target> and pin <team>/<name>`.

**Rationale**: design section 4.6 names `BuildBumpBundle` with exactly these parts and TD-12 says bump never calls the engine. R-25's "writes nothing" is simplest to prove when the dry-run path has nothing to write with; it also means a dry run works with the Docker environment misconfigured, as `deploy --dry-run` does. The dry run does not consult the registry, as the design's "call nothing" says, so it cannot report a missing version; the spec's Assumptions record this.

**Alternatives considered**: building the bundle with a nil backend for dry run was rejected because it would open `shrine.log` for a command that changes nothing. A `DryRun bool` in the bundle was rejected as a conditional in the handler where the deploy pattern already has two entry points.

## R6. What the operator sees: previous, new, and the terminal arm

**Decision**: before resolving, the handler reads `store.ImagePins.Get(team, name)`; `ErrImagePinNotFound` and a nil `ImagePins` mean no previous. After a successful resolution it prints one line to `Out`: `Bumped <team>/<name>: <previous> -> <new>; run "shrine deploy" to apply` when a previous pin existed, else `Pinned <team>/<name> at <new>; run "shrine deploy" to apply`. `<previous>` is `manifest.ReadableVersion(pin.Requested, manifest.DigestOf(pin.Pinned))` and `<new>` is `manifest.ReadableVersion(resolved.Requested, resolved.Digest)`, the same form the VERSION column and the `Pinned:` line use. Above it the observer renders the resolution as a deploy does: `🔎 Resolving image for <team>.<name> (<target>)`, the pull indicator, and the new `repinned` arm `  📌 Bumped <team>.<name> to <new>`. A failed resolution is returned as `<kind> "<name>": <backend error>`, the shape the engine's pre-pass uses, after the backend's own error event has rendered the cause.

**Rationale**: design section 4.6 step 5 fixes both success lines; section 4.9 fixes the `repinned` row. R-23 asks for previous and new; one readable form across the product is constitution VII. The previous pin is whatever is on record, including a pin for another repository, because "previous" means "what was recorded", and the next deploy would have replaced that pin anyway (T3's repository rule).

**Alternatives considered**: printing full digest references on the summary line was rejected: `describe` shows them, and the summary should match the table form the operator just read. Suppressing the observer during bump was rejected because the pull indicator is the only progress a slow pull shows.

## R7. The vanished-version message points at bump

**Decision**: `notServedError` becomes `pinned exact version "<pin.Pinned>" for <team>/<name> is no longer served by the registry; run "shrine bump <kind> <name>" to choose another version: <cause>`, with `<kind>` lower-cased from `op.Kind` so it names the subcommand (`application` or `resource`). The event, the `errors.Is` chain, and the no-digest failure are unchanged. The one integration assertion on the old clause (`AssertStderrContains("deploy the ")` in `TestPinnedImagePolicy`) is updated to the new clause; the backend unit test's expected string is updated.

**Rationale**: R-14's last sentence and T6-06; the ticket names this edit. The first clause stays so `TestPinnedImagePolicy`'s other assertions hold.

## R8. The integration suite

**Decision**: one new file, `tests/integration/bump_test.go`, `TestBump` on `newPinnedSuite` (same package, same registry world: `latest` is `whoami:v1.10.1` with its digest known). Helpers: `bump(tc, specsDir, args...)` runs `bump` with `--path` and `--state-dir`; `pushVersion(tc, w, tag)` pushes `whoami:v1.10.2` as `shrine/whoami:<tag>` and returns its digest; `pinLineFor(tc, name)` returns the artifact's `pins.txt` line. Scenarios, each cited by spec id:

1. (US1, US2, SC-001, SC-003) deploy; push `v2`; `bump app whoami-pinned -v v2`: success, stdout has `📌 Bumped <team>.whoami-pinned to v2@<new12>` and `Bumped <team>/whoami-pinned: latest@<old12> -> v2@<new12>; run "shrine deploy" to apply`; the app's pin line holds `<host>/shrine/whoami:v2` and `<host>/shrine/whoami@<newDigest>`; the resource's line is unchanged; the container id and `Config.Image` are unchanged; deploy prints `📌 Using pinned <team>.whoami-pinned v2@` and the container is recreated from `<host>/shrine/whoami@<newDigest>`; then `bump app whoami-pinned -v <oldDigest>`: `Bumped …: v2@<new12> -> <old12>; …`, deploy, container image is the old reference again.
2. (US1 scenario 4, SC-002) deploy; `bump app whoami-pinned -v v9`: failure, stderr contains `application "whoami-pinned"` and `pulling image "<host>/shrine/whoami:v9"`; `pins.txt` byte-identical; container id unchanged. Then `-v "not valid!"`: failure naming `invalid version`, `pins.txt` byte-identical, stdout has no `Resolving image`.
3. (US3, SC-004) deploy; push `v1.10.2` as `latest`; `bump res cache-pinned`: `Bumped <team>/cache-pinned: latest@<old12> -> latest@<new12>`; resource pin line holds the new digest; container untouched; a plain deploy afterwards applies it.
4. (US4, SC-005) `WriteManifestOwnedFixture` for the app: `bump app whoami-pinned -v v2` fails with `application "whoami-pinned": its version is manifest-owned (imagePullPolicy IfNotPresent); edit the manifest to change it`, with and without `--dry-run`; `bump app nope -v v2` fails with `application "nope": no manifest found in <specsDir>`; `bump app whoami-pinned --team other -v v2` fails with `not found in team "other"`; `pins.txt` does not exist after all three.
5. (US4 scenario 3, SC-006) no deploy; push `v2`; `bump app whoami-pinned -v v2`: `Pinned <team>/whoami-pinned at v2@<new12>; run "shrine deploy" to apply`, `pins.txt` holds one line, no container exists; deploy: the app container's image is `<host>/shrine/whoami@<newDigest>` and the output has `📌 Using pinned` for the app and `📌 Pinned` for the resource.
6. (US5, SC-007) deploy; push `v2`; `bump app whoami-pinned -v v2 --dry-run`: `[dry-run] would resolve <host>/shrine/whoami:v2 and pin <team>/whoami-pinned`, no `Resolving image`, no `📌`; `pins.txt` byte-identical; without `-v`: `would resolve <host>/shrine/whoami and pin …`.
7. (US6, SC-008) the existing "no longer served" scenario in `TestPinnedImagePolicy` asserts `run "shrine bump application whoami-pinned" to choose another version` instead of `deploy the `.

Written first, compile-checked with `go vet -tags integration ./tests/integration/...`, run only in CI.

**Rationale**: the ticket names six points and the registry fixture; the pinned suite's world already pushes versions and knows digests. Rollback and the vanished message are the spec's US2 and US6.

## R9. Documentation

**Decision**: per [contracts/docs-and-deviations.md](contracts/docs-and-deviations.md): `make docs-gen-cli` produces `docs/content/cli/bump.md`, `bump_application.md`, and `bump_resource.md` from the command help; the manifest reference's Image pull policy subsection gains a **Moving a pin.** paragraph and the vanished-version sentence now names the bump command; `AGENTS.md` gains the quick-start line, a `### shrine bump application/resource <name>` section, the `bump.go` entry in the project tree, and one clause in the pipeline note and the `pins.txt` line. There is no configuration change, so the configuration docs are untouched; the ticket's "configuration docs" item is satisfied by stating that. The operator guide is T8's.

## R10. Unit tests stay off the filesystem

**Decision**: the handler's pure pieces are unit-tested over an in-memory `planner.ManifestSet` built with `NewManifestSet` and `MergeManifest`, the existing `memTeamStore`, a `memImagePinStore` (new, same shape as the other fakes), and a recording `engine.ContainerBackend` stub: `findBumpArtifact` (found, unknown with the directory, team mismatch), `validateBumpVersion` (table), `buildBumpTarget` (tag, digest, empty, alias form, resource override), `prepareBump` after planning (manifest-owned refusal under a declared, a configured, and a derived policy; pinned passes), `bumpResolved` (op shape with `Repin`, previous read before, output line with and without a previous pin, error wrapping), and `formatBumpDryRun`. `Bump` and `BumpDryRun` themselves call `LoadDir` and are covered by the integration suite. The backend's repin branch is tested over `scriptedDockerAPI` and `fakePinStore` (pulls the target, records the pin with the injected clock, source `repinned`, alias expanded, digest target, no-digest error, pull failure leaves the pin, manifest-owned refusal). The terminal arm is one more byte-exact case. `BuildBumpBundle` joins the bundle-shape tests in `internal/app` (no engine, no vault, no plugin; slot prefixes; cleanup).
